# Lab 03. 카메라 → TFT 실시간 프리뷰 — Synaptics Astra SR110 (sr100_rdk/sr100/m55)

## 이 실습의 목표

지금까지의 카메라 실습(Lab 01/02)은 캡처한 이미지를 GDB 덤프나 통계 로그로만 확인했습니다. 이 실습은 **카메라로 캡처한 프레임을 물리 디스플레이(ST7789V3 TFT)에 흑백 이미지로 직접 표시**해서, 별도 PC 도구 없이 보드 하나로 "카메라가 지금 뭘 보고 있는지"를 눈으로 바로 확인합니다. 1초 간격으로 화면을 갱신하는 저속 라이브 프리뷰이고, 이 간격은 빌드/플래시 없이 콘솔 shell 명령으로 즉시 바꿔가며 테스트할 수 있습니다.

> **하드웨어 검증 상태**: SR110 RDK 실기에서 검증 완료. TFT 화면 전체(240x280)에 카메라 프리뷰가 여백 없이 표시되고, `preview interval set <ms>` shell 명령으로 갱신 간격을 실행 중에 바꾸는 것까지 확인했습니다. 개발 과정에서 겪은 두 가지 문제와 해결 방법은 [`TROUBLESHOOTING_kr.md`](./TROUBLESHOOTING_kr.md)에 정리했습니다.

## 사전 준비

- Lab 01/02와 마찬가지로 TFLM 등 AI용 west 모듈은 필요 없습니다 — 순수 Zephyr `video_api` + `spi`/`gpio` 기능만 사용합니다.
- 카메라 모듈이 SR110 RDK 보드에 이미 연결되어 있는 상태를 전제로 합니다(J23 커넥터, 별도 배선 불필요).
- **ST7789V3 TFT 모듈 + 레벨쉬프터가 필요합니다** — 아래 "TFT 배선" 참고.
- Lab 01/02를 먼저 해보셨다면 카메라 캡처 코드 구조가 낯설지 않을 것입니다 — 다만 이 실습만 따로 진행해도 아래 내용만으로 충분합니다.

## 이 실습에서 알아보고자 하는 것

- RAW8 Bayer 원시 데이터를 애플리케이션 코드에서 바로 가공해서, 별도 이미지 뷰어나 PC 도구 없이 임베디드 화면에 "그럴듯한" 이미지로 띄울 수 있는지
- 카메라(가로가 긴 480x270)와 TFT 패널(세로가 긴 240x280)처럼 화면비가 서로 다른 두 장치를 연결할 때, 이미지를 찌그러뜨리지 않으면서 화면 전체를 채우려면 어떻게 해야 하는지
- 서로 다른 두 주변장치(MIPI 카메라의 I2C1 제어선, TFT의 SPI0)가 한 애플리케이션 안에서 동시에 문제없이 동작하는지

## 배워야 하는 것 (핵심 학습 목표)

- 카메라(가로로 긴 16:9 계열)와 TFT 패널(세로로 긴 240x280)의 화면비가 다를 때, **회전 → 커버 크롭 → 스케일**을 한 번에 처리하는 방법: 90도 회전으로 두 장치의 "긴 변"끼리 맞춘 뒤, 화면비 차이만큼만 가장자리를 잘라내는(CSS의 `background-size: cover`나 사진 앱의 "채우기" 크롭과 같은 개념) 방식으로 화면 전체를 여백 없이, 왜곡 없이 채우는 기법
- 출력 픽셀 좌표 → (회전된 캔버스 좌표) → (원본 Bayer 좌표)로 이어지는 좌표 역변환을 순서대로 따라가는 방법, 그리고 최종적으로는 2x2 Bayer 블록의 짝수 좌표에 정렬시켜야 한다는 제약
- RAW8 Bayer의 2x2 블록(R, G, G, B) 4바이트를 평균 내면 "그 블록 하나의 대략적인 밝기"를 얻을 수 있다는 점 — 디베이어링과 밝기 근사를 한 번의 계산으로 처리하는 기법
- 그레이스케일 값 하나를 R=G=B로 채워 RGB565(2바이트/픽셀) 포맷으로 변환하는 방법과, `(gray>>3)<<11 | (gray>>2)<<5 | (gray>>3)` 같은 비트 시프트로 5/6/5비트 채널을 채우는 방식
- SPI0의 8바이트 FIFO 제약 아래에서 대량의 픽셀 데이터(수만~수십만 바이트)를 라인 단위로 청크 전송하는 패턴
- 카메라 스트림은 계속 백그라운드에서 흐르게 두고, 메인 루프가 그중 일부 프레임만 "샘플링"해서 화면에 반영하는 구조 — 초당 30프레임 카메라와 초당 1회 이하로 갱신되는 느린 디스플레이 사이의 속도 차이를 다루는 실용적인 방법
- Kconfig 값이 아니라 `atomic_t` 전역 변수 하나로 갱신 간격을 관리하고, Zephyr shell 명령(`preview interval set <ms>`)으로 그 값을 실행 중에 바꾸는 패턴 — 빌드/플래시 없이 파라미터를 즉시 실험해볼 수 있다는 실용적인 이점과, 서로 다른 스레드(메인 루프 vs shell)가 같은 변수를 안전하게 주고받으려면 왜 `atomic_t`가 필요한지

## 추가로 알면 좋은 내용

- 여기서 하는 변환은 진짜 디베이어링(demosaicing)이 아닙니다. 정식 디베이어링은 주변 픽셀을 보간(interpolation)해서 각 픽셀마다 완전한 R/G/B 세 값을 복원하지만, 이 실습은 2x2 블록을 통째로 평균 내서 컬러 정보 자체를 버리고 밝기(그레이스케일)만 남깁니다. 코드가 훨씬 단순해지는 대신 색은 전혀 보이지 않습니다 — Lab 02에서 "RAW8 원시 바이트 평균은 진짜 luma가 아니다"라고 정리했던 것과 같은 종류의 의도적 단순화입니다.
- 90도 회전 방향(시계 방향)은 `tft_preview.c`의 `rotate_to_bayer_coords()` 안에서만 결정됩니다. 실제 화면을 보고 카메라 방향과 반대로 돌아가 있거나 좌우가 바뀐 것처럼 보이면, 이 함수의 좌표 변환식만 바꾸면 됩니다(회전 방향을 반대로 하거나 축을 뒤집는 식) — 나머지 크롭/스케일 로직은 그대로 재사용됩니다.
- SPI0는 4MHz로 동작하고 한 프레임에 240×280×2바이트 = 134,400바이트를 보내야 하므로, 이론상 전송 시간만 최소 약 270ms입니다(오버헤드 제외). 갱신 간격을 너무 짧게(예: 300ms 이하) 잡으면 실제로는 화면 전송 자체가 못 따라가서 갱신 주기가 늘어질 수 있습니다 — 기본값 1000ms는 이런 여유를 감안한 값이고, `preview interval set <ms>` 명령으로 직접 짧게/길게 바꿔보면서 어느 지점부터 화면이 밀리기 시작하는지 체감해볼 수 있습니다.
- 카메라(I2C1)와 TFT(SPI0)는 물리적으로 완전히 분리된 핀이라 두 주변장치 사이에는 충돌이 없습니다. 다만 TFT를 켜는 순간 M55의 기본 콘솔(UART1, GPIO23/24 공유)을 잃는 것은 아래 "TFT 배선" 및 오버레이 설명 참고.

## 준비물

- Synaptics Astra SR110 RDK 보드 + OV02C10 카메라 모듈 (J23 커넥터로 이미 연결됨, 별도 배선 불필요)
- **ST7789V3 TFT 모듈 + 레벨쉬프터(TXS0108E 등)** — SR110은 신호가 1.8V, 이 TFT 모듈은 3.3V라서 레벨 시프터가 반드시 필요합니다. 자세한 배선은 아래 "TFT 배선" 참고.
- 외부 USB-TTL 어댑터 — TFT(SPI0)를 켜면 콘솔이 UART0 대체 핀(GPIO44/45, J24 13/14번 핀)으로 이동하므로, 로그를 보려면 필요합니다. (로그 없이 화면만 보셔도 실습은 가능합니다.)
- USB 케이블, PC (WSL2 + west CLI 개발 환경) 또는 PowerShell(Windows 네이티브) 빌드/플래시 환경

### TFT 배선 (SPI0, 레벨 시프터 경유)

SR110 쪽 신호는 1.8V, ST7789V3 TFT 모듈은 3.3V이므로 레벨 시프터(TXS0108E 등)를 반드시 거쳐야 합니다.

| 신호 | 역할 | SR110 쪽 (1.8V) | 레벨 시프터 | 디스플레이 쪽 (3.3V) |
|---|---|---|---|---|
| VCC | 전원 | - | - | 3.3V |
| GND | 그라운드 | GND | GND (양쪽 공통) | GND |
| SCL/SCLK | SPI 클럭 | SPI0 CLK (SoC GPIO22, J25 11번 핀) | CH_A ↔ CH_B | SCL |
| SDA/MOSI | SPI 데이터 | SPI0 MOSI (SoC GPIO23, J25 14번 핀) | CH_A ↔ CH_B | SDA |
| CS | 칩 셀렉트 | SPI0 CS, 네이티브 하드웨어 CS (SoC GPIO21, J25 12번 핀) | CH_A ↔ CH_B | CS |
| RES/RST | 리셋 | SoC GPIO17, J24 3번 핀 | CH_A ↔ CH_B | RES |
| DC | Data/Command 선택 | SoC GPIO18, J24 4번 핀 | CH_A ↔ CH_B | DC |
| BLK | 백라이트 | - | - | 3.3V (직결, 레벨 시프터 안 거침) |

레벨 시프터의 저전압 쪽(VCCA)은 1.8V, 고전압 쪽(VCCB)은 3.3V에 연결합니다. TXS0108E를 쓴다면 **OE 핀은 1.8V(VCCA)**에 연결하세요. MISO는 배선하지 않습니다 — 이 패널은 write-only입니다.

## 개념 — 캡처 → 회전+커버크롭 → 그레이스케일 → SPI 전송

```
video_dequeue() 로 WQVGA(480x270) RAW8 Bayer 프레임 도착
   ↓
[좌표 계산] 패널의 각 출력 픽셀(240x280)마다:
   1) 90도 회전한 캔버스(270x480) 기준 좌표로 변환
   2) 캔버스와 패널의 화면비 차이만큼 중앙을 기준으로 크롭 + 스케일된 위치 계산
   3) 그 위치를 다시 원본 Bayer 프레임의 짝수 (row, col)로 역변환
   ↓
[변환] 그 위치의 2x2 Bayer 블록(4바이트) 평균 → 그레이스케일 값 하나
   ↓
[변환] 그레이스케일 값을 R=G=B로 채운 RGB565(2바이트)로 변환
   ↓
[전송] 한 줄(240픽셀=480바이트)씩 8바이트 청크로 나눠 SPI0로 st7789_write_data() 전송 — 패널 전체(240x280) 채움
   ↓
video_enqueue() 로 버퍼 재사용, k_sleep(현재 간격) 후 다음 프레임으로 반복
```

카메라 자체는 `video_stream_start()` 이후 계속 초당 약 30프레임으로 백그라운드에서 캡처를 이어갑니다 — 메인 루프는 그중 매번 `video_dequeue()`로 가장 최근 프레임 하나만 꺼내 화면에 반영하고, 다음 프레임을 꺼내기 전에 현재 설정된 간격(기본 1000ms)만큼 잠듭니다. 즉 "카메라는 계속 찍고 있지만, 화면은 그중 일부만 골라서 보여준다"는 구조입니다.

### 갱신 간격을 실행 중에 바꾸기 (Shell)

이 랩은 갱신 간격을 코드에 하드코딩하지 않고 `atomic_t` 전역 변수(`g_preview_interval_ms`)로 관리하고, Zephyr shell 명령으로 그 값을 바로 바꿀 수 있게 만들었습니다. 콘솔(외부 USB-TTL 어댑터, UART0 대체 핀)에서:

```
uart:~$ preview interval get
preview interval: 1000 ms

uart:~$ preview interval set 2000
preview interval set to 2000 ms (takes effect on the next frame)

uart:~$ preview interval set 300
preview interval set to 300 ms (takes effect on the next frame)
```

빌드/플래시 없이 바로 반영되므로, 화면이 매끄럽게 보이는 지점과 너무 빨라서(또는 시리얼이 너무 바빠져서) 밀리기 시작하는 지점을 직접 찾아볼 수 있습니다. 허용 범위는 100~10000ms이고, 범위를 벗어나거나 숫자가 아닌 값을 넣으면 에러 메시지만 출력되고 기존 값이 유지됩니다.

## Step 1. 빌드 및 플래시

`lab/`가 준비되어 있습니다. 추가 옵션 없이 바로 빌드할 수 있습니다.

```bash
west build -p always -b sr100_rdk/sr100/m55 -s <워크스페이스>/SR110_Zephyr_camera/03_tft_preview/lab -d build_camera_tft_preview
```

콤바인 이미지를 평소처럼 `openocd_flash.py`로 플래시합니다.

## Step 2. 실행 & 확인

TFT 화면 **전체(240x280)**에 카메라가 보고 있는 장면이 흑백으로 표시되고, 기본 1초 간격으로 갱신됩니다. 카메라 이미지가 90도 회전되어 표시되며, 화면비 차이 때문에 원래 화각의 가장자리 일부는 잘려서 보이지 않습니다.

콘솔(외부 USB-TTL 어댑터, UART0 대체 핀)에는 아래와 같이 짧은 로그만 출력됩니다.

```
*** Booting Zephyr OS build v4.4.1 ***
[00:00:00.xxx,000] <inf> camera_tft_preview: === SR110 Camera TFT Preview (interval=1000 ms, 'preview interval set <ms>' to change) ===
[00:00:01.xxx,000] <inf> camera_tft_preview: Frame 1: capture -> display
[00:00:02.xxx,000] <inf> camera_tft_preview: Frame 2: capture -> display
[00:00:03.xxx,000] <inf> camera_tft_preview: Frame 3: capture -> display
...
```

확인할 포인트:

- TFT 화면 **전체**(위/아래/좌우 가장자리까지)에 흑백 이미지가 뜨는지
- 카메라 렌즈를 손으로 가리면 화면이 어두워지는지
- 화면에 비치는 방향이 실제 카메라 방향과 90도 돌아가 있는 게 맞는지(의도된 동작입니다) — 만약 상하좌우가 기대와 다르게 뒤집혀 보인다면 "추가로 알면 좋은 내용"에 적힌 대로 `rotate_to_bayer_coords()`만 수정하면 됩니다
- 손이나 물체를 카메라 앞에서 움직이면 약 1~2초 지연을 두고 화면에 반영되는지 (실시간 스트리밍이 아니라 저속 프리뷰라는 것을 체감)
- `Frame N: capture -> display` 로그가 한 줄씩 꾸준히 늘어나며, 타임아웃 에러 없이 계속 동작하는지 (이 실습은 Lab 02와 달리 고정 프레임 수 없이 계속 실행됩니다 — 리셋 전까지 무한 반복)
- `preview interval set <ms>`로 간격을 바꿔보면 화면 갱신 속도와 로그 출력 속도가 그에 맞게 즉시 바뀌는지
