# Lab 03 트러블슈팅 — 카메라 → TFT 실시간 프리뷰

실기 검증 과정에서 발견되고 수정된 두 가지 이슈를 정리합니다.

## 1. TFT 화면 절반만 표시되던 문제

**증상**: 초기 버전은 카메라 프레임(480x270)을 단순히 2로 나눈 240x135 크기로만 계산해서 패널의 왼쪽 위에만 그렸습니다. 결과적으로 패널의 세로 하단 절반(135~280행)이 항상 빈 화면(초기화 색)으로 남았습니다.

**원인**: 카메라(가로가 긴 480x270)와 TFT 패널(세로가 긴 240x280)의 화면비가 서로 다른데, 단순 다운스케일(÷2)만 적용하고 화면비 차이를 처리하지 않았기 때문입니다. 240x135는 패널 가로(240)와는 우연히 맞았지만 세로(280)의 절반에도 못 미칩니다.

**해결**: 카메라 이미지를 90도 회전해서 카메라의 긴 변(480)을 패널의 긴 변(280)에 맞춘 다음, 두 화면비 차이만큼만 중앙 기준으로 잘라내는 "커버 크롭"(CSS의 `background-size: cover`나 사진 앱의 "채우기" 크롭과 같은 개념) 방식으로 다시 설계했습니다. 좌표 변환은 출력 픽셀(240x280) → 회전된 캔버스 좌표(270x480) → 원본 Bayer 좌표 순으로 역산하며, 최종 좌표는 2x2 Bayer 블록에 맞춰 짝수로 정렬합니다. 그 결과 패널 전체를 여백 없이 채우게 되었지만, 대가로 원본 화각의 가장자리 일부(회전 후 화면비 차이만큼)는 항상 잘려서 보이지 않습니다 — 화면을 꽉 채우는 것과 전체 화각을 다 보여주는 것은 화면비가 다른 이상 동시에 만족할 수 없다는 점을 보여주는 예입니다.

## 2. 화면/시리얼 로그가 너무 잦아 알아보기 어렵던 문제

**증상**: 초기 설계는 매 프레임 캡처마다 여러 줄의 로그(비디오 캡스, 포맷, 10프레임마다 요약 등)를 찍었습니다. 갱신 간격이 짧을 때 시리얼 출력이 화면 갱신과 뒤섞여 콘솔도 화면도 알아보기 어려웠습니다.

**원인**: Lab 01/02 스타일의 상세 로깅을 그대로 이어받았는데, 이 랩은 무한 반복 라이브 프리뷰라서 로그가 끊임없이 누적되는 구조였습니다. 또한 초기 갱신 간격(0.5초)이 SPI0 전송 시간(패널 전체 기준 이론상 최소 약 270ms)에 비해 여유가 크지 않았습니다.

**해결**: 부팅 시 한 번 나오는 초기화 로그를 빼면, 매 사이클마다 `Frame N: capture -> display` 한 줄만 남기도록 로그를 줄였습니다. 또한 기본 갱신 간격을 0.5초 → 1초로 늘려 SPI 전송에 여유를 뒀습니다. 이 간격을 Kconfig 상수가 아니라 `atomic_t` 전역 변수 + Zephyr shell 명령(`preview interval get/set`)으로 바꿔서, 빌드/플래시 없이 실행 중에 바로 조정하며 어느 지점부터 화면이 밀리기 시작하는지 실험할 수 있게 했습니다.
